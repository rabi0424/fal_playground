# fal playground

[fal.ai](https://fal.ai) と Modal 自前ホスト版 Krea 2（[modal_comfy](https://github.com/rabi0424/modal_comfy)）の画像生成 API を使う個人用プレイグラウンド。Cloudflare Workers（Git 連携デプロイ）でのホストを前提に、認証は Cloudflare Access（メール認証）、API キー類はすべて Worker の Secret に置きます。ブラウザ側でのキー入力・保存はありません。

## 初期設定

### 1. Cloudflare Access で保護する（必須）

> **重要**: この設定をせずにデプロイすると、fal プロキシなどの API が URL を知っている全員に開放された状態になります（fal キーの無断利用につながる）。必ず最初に設定してください。

1. Cloudflare ダッシュボード → **Workers & Pages** → 対象の Worker → **Settings** → **Domains & Routes**
2. workers.dev の行の **Enable Cloudflare Access**（Cloudflare Access を有効化）をオン
3. 自動作成された Zero Trust アプリケーションのポリシーを編集し、**自分のメールアドレスのみ許可**（ログイン方法: One-time PIN）にする
4. セッション期間は好みで（例: 1 か月。切れたら再度メール認証するだけ）

以後、どの端末からでも「URL を開く → メールに届く PIN を入力」だけで使えます。

### 2. Secret を設定する

Cloudflare ダッシュボード → 対象の Worker → **Settings** → **Variables and Secrets** に、Type: **Secret** で追加:

| Variable name | 値 | 用途 |
|---|---|---|
| `FAL_KEY` | [fal.ai ダッシュボード](https://fal.ai/dashboard/keys)で発行した API キー（`key_id:key_secret`） | fal での生成 |
| `WAVESPEED_API_KEY` | [WaveSpeed](https://wavespeed.ai/) のダッシュボードで発行した API キー | 画像編集（WaveSpeed を選んだとき）|
| `RUNWARE_API_KEY` | [Runware](https://runware.ai/) のダッシュボードで発行した API キー | 画像編集（Runware を選んだとき）|
| `MODAL_PROXY_KEY` | Modal の Proxy Auth Token（`wk-…`） | Modal 版 Krea 2 での生成 |
| `MODAL_PROXY_SECRET` | 同上（`ws-…`）。[Modal ダッシュボード → Settings → Proxy Auth Tokens](https://modal.com/settings) で発行 | 同上 |
| `POE_API_KEY` | [poe.com/api_key](https://poe.com/api_key) で発行した Poe の API キー | 部分AI編集（課金は Poe ポイント） |
| `HF_TOKEN` | [Hugging Face のアクセストークン](https://huggingface.co/settings/tokens)（対象リポジトリへの **write** 権限） | Civitai からの LoRA 取り込み |
| `CIVITAI_TOKEN` | [Civitai のアカウント設定 → API Keys](https://civitai.com/user/account) で発行 | 同上（Civitai のダウンロードはほぼログイン必須） |

旧バージョンで使っていた `SYNC_TOKEN` は不要になったので削除して構いません。

### 3. R2 バケットを作成する（生成画像の保存先）

生成画像は R2 に保存します。デプロイ前に `wrangler.jsonc` の `r2_buckets` と同名のバケットを作成してください（未作成だとデプロイに失敗します）。

```
npx wrangler r2 bucket create fal-playground-images
```

画像は保存後に内容が変わらないので、コストが気になる場合は R2 側でエイジングのライフサイクルルールを設定して古い孤児画像を自動削除しても構いません（履歴と連動した削除は Worker が行います）。

### 4. D1 データベースを作成する（生成履歴のカタログ）

生成履歴（プロンプト・設定・画像への参照）は D1 に置きます。**このリポジトリの `wrangler.jsonc` には作成済みの `database_id` が入っているので、通常この手順は不要です。** 別のアカウントで一から立てるときだけ、作成して `database_id` を差し替えてください（未設定だとデプロイに失敗します）。

ダッシュボードなら **Storage & Databases → D1 SQL Database → Create Database**（名前は `fal-playground`）。CLI なら次のとおりです。

```
npx wrangler d1 create fal-playground
```

`database_id` はダッシュボードでデータベースを開いたときの URL の末尾（`.../databases/<ここ>/...`）にも出ています。

表は Worker が最初に履歴へ触れたときに作ります（Git 連携デプロイでは wrangler の migrations が走らないため）。定義は `schema.sql` にも置いてあるので、手で流したい場合は次のとおりです。

```
npx wrangler d1 execute fal-playground --remote --file=schema.sql
```

**以前のバージョンから更新する場合、Durable Object に貯まっている履歴は自動で D1 へ移ります**（新しい方から順に、何回かのアクセスに分けて。移行の途中でもギャラリーの先頭は揃っています）。作業は要りません。

## 機能

- モデル選択（FLUX 系 / Recraft V3 / Modal 自前ホスト版 Krea 2 / 任意のカスタムモデル ID）
- サイズ（約 1MP 基準のプリセット 6 種 + カスタム px 指定）・枚数・シード（「固定」チェック時のみ適用）・ステップ数・ガイダンスの指定
- Hugging Face 公開リポジトリからの LoRA 一括登録（.safetensors を一覧表示して選択）
- Civitai からの LoRA 取り込み（URL を貼ると Hugging Face へアップロードしてライブラリに登録・下記参照）
- 画像編集（Qwen Image Edit 2511 + LoRA / FLUX.1 Fill [dev] OneReward / Wan2.2 + VACE / LanPaint。画像 1 枚と指示文で編集・下記参照）
- LoRA 比較アリーナ（別画面 `arena.html`・下記参照）
- 部分AI編集（別画面 `edit.html`・下記参照）
- 生成履歴とプロンプトの再利用（サーバー保存・全端末で共通）
- 生成時間の統計（サイドバー「統計」。アクセスポイント別の平均・中央値・分布。Modal 版は順次処理の待ち時間を除いた実処理時間で集計し、過去の記録も完了時刻から逆算して補正）
- 開閉式の左サイドバー（全画面共通のナビゲーション。畳むとアイコンだけのレールになる・Cmd/Ctrl + B で開閉・スマホでは引き出し）
- ダークモード（自動 / ライト / ダーク切替。サイドバー下部の 3 択）
- Cmd/Ctrl + Enter で生成
- スマホ対応（iPhone 16 想定・下部固定の生成バー・ライトボックスのスワイプ切替・左端からの払いでサイドバーを開く）

## Civitai からの LoRA 取り込み

LoRA 欄の「Civitai から取り込み」で、Civitai のモデルページ URL（`modelVersionId` 付き可）またはダウンロード URL を貼ると、Worker がサーバー側でモデルをダウンロードして Hugging Face リポジトリへアップロードし、完了時に LoRA ライブラリへ自動登録します。

- 「確認」でモデル名・バージョン・ファイルサイズに加え、保存されるサイト情報（トリガーワード・作者・説明・サンプルの生成設定と JSON 全文）をプレビューしてから開始できます。同じ内容（SHA256 一致）が既にリポジトリにある場合はアップロードせず登録だけ行います
- 既定で、その時点のサイト情報を `<ファイル名>.civitai.json` としてモデルの隣に保存します（トリガーワードなどを後から調べるため。画像本体は保存せず URL と生成設定のみ）。ダイアログのチェックを外すと保存しません（開き直すと ON に戻ります）。本体がアップロード済みで JSON だけ無い場合は JSON のみ追加されるため、メタデータの後付け取り込みにも使えます
- 処理はサーバー側で完結するので、開始後にタブを閉じても続行されます（次回アクセス時に完了を検知して登録）
- 進行中は「取り込みを中止」ボタンが出ます（サーバー側のジョブも止めて一時ファイルを破棄します）。うまく進まないときは `/api/lora-import/jobs` をブラウザで開くと、各ジョブの段階・転送量・最後に前進してからの秒数・alarm の状態（`alarmOverdue` が `true` なら alarm が配信されないまま残っている）が JSON で確認できます
- 進捗はブラウザが定期的に問い合わせて表示します（ダイアログを開いている間は 2 秒間隔、閉じている・タブが裏にある間は 30 秒間隔）。取り込みが 15 分まったく進まなかった場合はサーバー側でジョブを中断してエラーを表示し、一時ファイルも破棄します
- ダウンロード後に SHA256 を Civitai の公称値と照合してからアップロードします
- 制約・注意:
  - `HF_TOKEN`（write）が必須。`CIVITAI_TOKEN` も実質必須です（未設定だと多くのモデルでダウンロードが拒否されます）。Early Access（有料先行）中のモデルは取り込めません
  - civitai.red などのミラー URL も受け付けますが、API 互換性が無い場合はダウンロード URL の直接指定を使ってください
  - **公開リポジトリへのアップロードは再配布に当たります**。モデルのライセンスを確認のうえ利用してください。なお非公開リポジトリを取り込み先にすると、fal は認証付き URL をダウンロードできないため fal 系モデルでその LoRA は使えません（Modal 版は modal_comfy 側の設定次第）

## 画像編集

トップの「画像編集」（`imgedit.html`）で、画像 1 枚と指示文を渡して編集します。範囲を切り抜いてはめ込む「部分AI編集」（Poe）とは別の機能で、画像全体をモデルに渡します。

**プロバイダは fal / WaveSpeed / Runware / Modal（2 種）から選べます**。fal と WaveSpeed は同じ Qwen Image Edit 2511（API の形と課金が違うだけ）で、Runware と Modal は**マスクした範囲を描き直す**モデルです。

| | fal（`fal-ai/qwen-image-edit-2511/lora`） | WaveSpeed（`wavespeed-ai/qwen-image/edit-2511-lora`） | Runware（`runware:121@1`） | Modal（自前ホスト） | Modal（自前ホスト） |
|---|---|---|---|---|---|
| モデル | Qwen Image Edit 2511 | Qwen Image Edit 2511 | FLUX.1 Fill [dev] OneReward | Wan2.2 + VACE | LanPaint（Krea 2） |
| 得意なこと | 画像全体への指示 | 画像全体への指示 | 塗った範囲だけの描き直し・物体の除去 | 塗った範囲の描き直し（動画モデル譲りの整合性） | 塗った範囲の描き直し（**生成と同じ Krea 2 の LoRA が効く**） |
| 指定できるもの | 解像度・枚数・ステップ・ガイダンス・速度・negative prompt・seed・形式 | 指示文・LoRA・seed・形式のみ | 解像度・枚数・ステップ・CFG・True CFG・マスクの余白・スケジューラ・出力品質・negative prompt・seed・形式 | 解像度・ステップ・CFG・shift・マスクを広げる px・negative prompt・seed・形式 | 解像度・思考回数・ステップ・境界ブレンド px・マスクを広げる px・切り抜きの余白 px・seed・形式 |
| 出力枚数 | 1〜4 | 1 枚固定 | 1〜4 | 1 枚固定 | 1 枚固定 |
| マスク | ブラウザ側の合成のみ（ずれ補正・色合わせあり） | ブラウザ側の合成のみ（ずれ補正・色合わせあり） | **API に渡す（必須）** + 合成（色合わせあり） | **API に渡す（必須）** + 合成（ずれ補正・色合わせあり） | **API に渡す（必須）**。マスクの外は元画像のまま返る。**塗った範囲のまわりだけを切り抜いて送れる**（既定で有効） |
| LoRA | 使える（ライブラリ） | 使える（ライブラリ・公開 URL のみ） | 使える（Runware 登録済みの AIR） | 蒸留 LoRA 2 本 + ライブラリから最大 8 個（下記） | ライブラリから最大 8 個（Krea 2 用） |
| 課金 | $0.035 / メガピクセル（解像度依存） | $0.025 / 枚（固定） | 生成後に実額を表示 | 自前ホスト（GPU の秒課金） | 自前ホスト（GPU の秒課金） |
| 必要な Secret | `FAL_KEY` | `WAVESPEED_API_KEY` | `RUNWARE_API_KEY` | `MODAL_PROXY_KEY` / `MODAL_PROXY_SECRET` | `MODAL_PROXY_KEY` / `MODAL_PROXY_SECRET` |

プロバイダを切り替えると、対応していない項目は自動で隠れます。大きい画像を少数編集するなら WaveSpeed、細かく詰めたいなら fal、一部だけを描き直したいなら Runware か Modal、という使い分けになります。**キャラクター LoRA を効かせたまま顔や服だけ描き直したい**なら LanPaint です（生成で使っている LoRA がそのまま使えます）。

#### Modal（Wan2.2 + VACE）

生成側の「統合版」と**同じコンテナを共有**します（片方を使えばもう片方もウォームになります）。VACE はマスクの中だけを描くのではなく**画面全体を再生成**し、生の再生成画像をそのまま返すので、マスクの内側だけを元画像に重ねる合成はブラウザ側で行います（ほかのプロバイダと同じ仕組みなので、塗り直しは作り直さずに反映されます）。

- 送信サイズは **32 の倍数**に丸めます。Wan がその解像度しか扱えないためで、最初から合わせて送ることで丸めのズレを避けています
- モデルへ渡すマスクは**ハードエッジ**です。半透明の縁をそのまま渡すと、消したいものの輪郭がゴーストとして残ったり、境界に暗い縁取りが出たりします。ぼかしは合成のときだけかけ、輪郭のリークには「マスクを広げる（px）」を使います
- 蒸留 LoRA（`lightx2v cfg_step_distill` / `FusionX`）を強度 0.4 で**常時適用**します。CFG 1・20 ステップという既定はこの構成が前提で、外すと出力が破綻します。値を毎回同じにしているので ComfyUI のキャッシュが効き、モデルの再ロード（数十秒）も起きません
- その上に**ライブラリから Wan 用の LoRA を最大 8 個**まで重ねられます（蒸留 2 本と合わせて API のサニティ上限 10 本）。ライブラリの項目は **Hugging Face の resolve URL のまま**送るので、どのリポジトリから取り込んだものでも、Modal Volume に無ければ初回リクエスト時に取り込まれます（サブフォルダに置かれたファイルも同じ）。この画面から「Hugging Face から一括登録」「Civitai から取り込み」もできます
- LoRA の候補はベースモデルで絞られます。**Qwen 用の LoRA は Wan では使えない**ので、登録時に「Wan」を選んでください。Civitai から取り込んだものは Civitai 側の表記から自動で判別します（`Wan Video 14B t2v` のような 2.1 系の表記も、`Wan Video 2.2 …` と同じ「Wan」として扱います）。プロバイダを切り替えると、そのモデルで使えない LoRA 行は自動で外れます
- ライブラリを通さず、**「名前を直接入力…」で LoRA 名を打つこともできます**。この API は名前でも LoRA を指定できるので、ベースモデルの表記に関係なく使えます。ただし名前だけで渡した場合に Modal が探すのは Volume と既定リポジトリ（`tottie2215/temp_str`）の**直下**だけなので、そこに無い名前は `lora '...' not found in volume` になります。別のリポジトリのものは名前ではなくライブラリ経由（URL）で指定してください
- **非公開リポジトリの LoRA は使えません**。チェックポイントと違い、modal_comfy 側が LoRA の取得に `hf_token` を使わないためです（公開リポジトリなら問題ありません）
- 編集は 900 秒級の処理で、150 秒を超えると Modal が結果ポーリング用の URL を返します。そのため生成と同じく **Worker 側のジョブ**にしてあり、タブを閉じても結果は失われません
- ポーリング先は、関数が終わるまで **202 Accepted**（本文なし）を返します。`res.ok` は 202 でも真なので、ここを分けずに扱うと**空の本文を画像として保存し、壊れた結果が「完了」になります**。返ってきた本文が PNG かどうかも確かめてから保存します
- 走り続けているジョブは **30 分**で打ち切ってエラーにします（編集の 900 秒級に対して十分な余裕を取った上限）。また、クライアントが状態を問い合わせたときに alarm が落ちていれば張り直します。どちらも「モデル側は終わっているのに画面が『編集中…』のまま進まない」状態を残さないためのものです

#### Modal（LanPaint インペイント）

Krea 2 のインペイントです（modal_comfy の `lanpaint-api` の `/inpaint`）。Wan2.2 + VACE とは違い**塗った範囲だけを描き直し**、マスクの外は元画像と**ピクセル一致**で返ります（サーバー側で合成済み・実測の平均差 0.00）。投入・ポーリング・打ち切りの仕組みは Wan2.2 + VACE と同じ Worker のジョブを共用していて、送り先だけが `/edit` と `/inpaint` に分かれます。

- **生成で使っている Krea 2 の LoRA がそのまま効きます**。キャラクター LoRA を当てたまま顔や服だけ描き直す、という使い方はこちらが向きます（Wan2.2 + VACE の LoRA は Wan 用なので、生成側の LoRA は使えません）
- **指示文には「塗った範囲に何があってほしいか」だけを書きます**（例:「赤いニット帽」）。LanPaint はプロンプトへの依存が強く、「帽子をかぶった男性の写真」のような画像全体の説明を書くと結果が悪くなります。画面でも指示文の欄の下でこれを断っています
- 実質のノブは**「思考回数」（`num_steps`・既定 5）だけ**です。塗った範囲をまわりと辻褄合わせするために考え直す回数で、生成時間はこれにほぼ比例します（実測 832×1216 / RTX PRO 6000 で `6.9 + 4.97 × 思考回数` 秒）。簡単な差し替えなら 2〜3、難しいものは 10 で、0 にすると LanPaint を切った状態（ただの修復）になります。いま何秒くらいかかるかは、詳細設定と実行バーの費用欄にその場で出ます
- マスクは**二値**で渡します（LanPaint 公式 README の "requires binary masks ... without opacity or smoothing"）。ぼかした縁をそのまま渡さない点は Wan2.2 + VACE と同じで、ぼかしは合成のときだけかけます。境界のなじみは API 側の**境界ブレンド px**（`blend_overlap`・既定 9・**奇数のみ**）が担当します。偶数を打たれた場合は 422 にならないよう +1 して送ります
- 送信サイズは Wan と同じく **32 の倍数**に丸めます（LanPaint 側でも丸められるので、最初から合わせて送って丸めのズレを避けます）
- **ずれの補正は要りません**。マスクの外が元画像のまま返るので、そもそもずれません（チェックも出ません）
- CFG・サンプラー・スケジューラ・denoise は既定のままにしてあり、画面には出していません。特に CFG は 1.0 から上げると内部の評価回数が 2 倍になり、単純に 2 倍遅くなります
- **Wan2.2 + VACE とは別のコンテナ**です。両方を使うとコンテナが 2 つ立ち上がるので（モデルが別物で統合できないため）、LanPaint に寄せるなら生成側も「Modal LanPaint 版」を選ぶとコンテナ 1 つで収まります
- コールドスタートは 35〜60 秒 + 生成時間です
- **塗った範囲のまわりだけを切り抜いて送ります**（既定で有効・下記）

- 入力画像は**端末から**（ファイル / カメラ / ドラッグ＆ドロップ）か**生成履歴から**選べます。長辺 2048px に収まるよう縮小してから送ります
- LoRA を最大 3 つまで指定できます（Modal の 2 つだけは 8 つ）。fal / WaveSpeed は共通の LoRA ライブラリ（表示名・既定 scale・トリガーワードがそのまま使えます）から選び、**候補に出るのはそのモデルのベース用の LoRA だけ**です（fal / WaveSpeed は Qwen、Wan2.2 + VACE は Wan、LanPaint は Krea 2）。この画面からも「Hugging Face から一括登録」「Civitai から取り込み」で追加できます。Runware は指定の仕方が違うので、下記の専用の欄になります
- fal では出力サイズを既定で入力画像に合わせます。ステップ（28）・ガイダンス（4.5）・速度（acceleration）・seed・negative prompt も指定できます。出力形式（PNG / JPEG / WebP）はどのプロバイダでも指定できます（WaveSpeed と Runware の既定は JPEG なので、劣化させないよう常に明示して送ります）
- Runware の生成パラメータは下記の「Runware の推奨設定」を既定にしています。送信サイズは 64 の倍数（128〜2048）に丸めて送ります
- **実行バーは画面の下端に常駐します**（生成画面と同じ扱い）。結果を見ながらでも、スクロール位置に関わらず次を流せます
- **順番待ちに積めます。**「編集する」を押しても完了は待たず、続けて次を送れます（同時に流せるのは 5 件まで）。送信中にページを閉じても、開き直せば順番待ちのぶんまで回収します
- 走っているぶんはバーの上に**1 件 = 1 行**で並びます。状態・プロンプト・**経過秒**・✕ を横一列に置き、折り返しません（待っているだけで実行バーが画面を押し上げないように）。経過秒はポーリング間隔とは別に 1 秒ごとに数え直すので、止まっていないことが分かります。収まらない文字は省略表示になり、押すと全文が出ます。✕ でその編集の結果を受け取るのをやめられます（モデル側の処理は止まりません）
- 実行バーに**費用の目安**を出します。fal は解像度から、WaveSpeed は枚数から計算します。Runware は単価を事前に出せないので、代わりに `includeCost` で返る**実額を結果に表示**します
- fal で安全性チェックに引っかかった画像は塗り潰されて返るため、その旨を表示します（WaveSpeed の API にはこのフラグがありません）
- 結果は生成履歴（`type: 'imgedit'`）に保存され、生成画面のギャラリーにも並びます。入力画像も一緒に残るので、後から何を編集したか分かります
- 画面下の**編集履歴のサムネイルは、押すと拡大表示**になります（合成結果 → 生成結果そのまま → 入力画像の順に、← → とスワイプで送れます）。入力画像への転用や「マスクを調整」は**右上の ⋯ から**選びます（押しただけで入力画像が入れ替わると、見比べたいだけのときに戻せないため）
- 「この結果を編集」で、出力をそのまま次の入力にできます

#### 切り抜いて送る（LanPaint）

塗った範囲が画像の一部でしかないとき、画像ぜんぶを送るとモデルの解像度はその一部にほとんど回りません。そこで**塗った範囲のまわりだけを切り抜いて送信サイズいっぱいに使い**、返ってきた画像を合成のときに元の位置へ戻します。同じ秒数でも、描き直したい場所に使える画素が増えます（Runware の `maskMargin` が内部でやっていることを、こちらの都合で持てるようにしたものです）。**既定で有効**で、チェックで切れます。

- 枠は**塗った範囲（ぼかしの届く先まで）の外接矩形 + 余白**です。マスクエディタに**破線と四隅のつまみだけ**を描き、塗っている最中もその場で追従します
- **「切り抜きの余白（px）」**で、塗った範囲の外側にどれだけ元画像を残すかを決めます（元画像の px・既定 64）。周りの文脈が要る編集ほど広めに取ってください
- 枠は**送信サイズの縦横比に合わせて広げます**（引き伸ばして送らないため）。「送信サイズ」が「自動」のときは、元画像ではなく**切り抜く範囲の比**でプリセットを選びます。画像の端で打ち止めになって比が崩れたときは、もう一方の辺を詰めて比を取り戻します。**譲るのは余白だけで、塗った範囲そのものは必ず枠に入れます**（入りきらないときだけ、これまでどおり引き伸ばして送ります）
- 狭く塗ったときに小さすぎる範囲を送信サイズまで引き伸ばすと、ぼやけた画像をモデルに見せることになるので、**自動で決めた枠は送信サイズの 1/4 を下限**にします（何倍で送るかは欄の下と結果の見出しに出ます）
- **四隅のつまみをドラッグすると枠を手で決められます**（指でも押せます）。手で動かすと自動追従は止まり、「自動に戻す」で戻せます。つまみを押しただけ（動かさずに離した）では何も変わりません
- マスクが枠からはみ出していると警告を出します（はみ出したぶんは描き直されません）
- 枠が画像ぜんぶを含むときは切り抜かずに送ります（「全面」で塗ったときなど）
- 合成・ずれ補正・色合わせは、切り抜いた範囲を土俵にして行います。**塗り直したときの合成し直しも、記録に残した切り抜き範囲（`region`）を使う**ので作り直しは要りません

#### 色合わせ（マスクを使うとき）

画像全体を作り直すモデルは、マスクの外側も「元画像に似せて描き直したもの」なので、露出やホワイトバランスが全体にわずかに動きます。内側だけを貼り戻すと、その差が継ぎ目として出ます。そこで、重ねる前に編集結果の色味を元画像へ寄せます（マスクを使うときだけ・チェックで無効化できます）。

- **合わせる先は元画像、比べる場所はマスクの外側だけ**です。ここは両方が同じものを写しているはずの領域なので、「写っているものが違う」内側を混ぜずに済みます。境目は編集がにじむので、ずれ補正と同じく広めに除きます
- 変換はチャンネルごとの 1 次式で、**中央値と幅（10〜90 パーセンタイル）を合わせます**。平均と標準偏差ではなく百分位を使うのは、除ききれずに残ったにじみに引っ張られないためです。3×3 行列やヒストグラム一致まで踏み込むと、参照が少ないときに階調が崩れます
- 「合成 → その結果へ寄せる → もう一度」と繰り返す手もありますが、**合わせる先（元画像のマスク外）は毎回同じなので 1 回で解いた答えに収束します**。むしろ繰り返すほど合成済みの内側が参照に混じり、補正が弱まります。なので 1 回で決めています
- 全面を塗った場合など、比べられる場所が足りないときは何もしません（合わせる先が無いため）
- 補正量には上限を設けています（幅は 1/1.6〜1.6 倍、中央値の移動は ±64）。推定が壊れたときに、かえって悪化させないためです
- 結果を出したあとでもチェックを切り替えれば、その場で合成し直します（塗り直しと同じ扱い）

合成解像度 400×300 の検証では、色味を動かした編集結果とオリジナルのマスク外側の平均絶対差が **13.0 → 0.24**（0〜255）まで縮みました。

#### ずれの補正（fal / WaveSpeed / Modal の Wan2.2 + VACE）

Qwen Image Edit も Wan2.2 + VACE も画像全体を作り直すので、**返ってくる絵が数 px ずれることがあります**（LanPaint はマスクの外が元画像のまま返るので対象外です）。そのままマスクで抜くと、差し替えた部分だけ位置がずれて見えます。そこで重ねる前に位置を合わせます（マスクを使うときだけ・チェックで無効化できます）。

- **マスクの外側**（＝変わらないはずの領域。境目は編集の影響を受けるので広めに除く）だけを見ます
- 明るさやコントラストの違いに引きずられないよう、輝度そのものではなく**勾配**（輪郭の出方）を正規化相互相関で比べます
- 長辺 192px で粗く探し、512px で詰め、最後に相関のピークを**放物線で近似して副画素まで**読みます（ずれは 1px 未満のことも多いため）
- 相関が低い（＝手がかりが無い）ときや、ずれが 1/4 画素未満のときは動かしません
- 測ったずれは記録に残すので、マスクを塗り直しても測り直しません。結果の見出しに「ずれ補正 -4.09, +2.78 px」のように出ます

合成用に 1 枚あたり 0.5 秒ほど増えます。

### Runware の推奨設定（FLUX.1 Fill [dev] OneReward）

**このモデルは素の FLUX.1 Fill [dev] とは推奨値がまるで違います。** 素の FLUX.1 Fill は内蔵ガイダンス（`CFGScale`）を 30 前後で使いますが、OneReward は**内蔵ガイダンスを 1 まで下げて、本来の CFG（`trueCFGScale`）を効かせる**前提で学習されています。公式の作例（[bytedance-research/OneReward](https://huggingface.co/bytedance-research/OneReward)）は `guidance_scale=1.0` / `true_cfg=4.0` / `num_inference_steps=50` です。

| 項目 | 既定値 | 根拠 |
|---|---|---|
| ステップ | 50 | 公式作例と同じ |
| CFG（`CFGScale`） | 1 | 公式作例の `guidance_scale=1.0`。FLUX の内蔵ガイダンスなので、上げても効きません |
| True CFG（`trueCFGScale`） | 4 | 公式作例の `true_cfg=4.0`。**これを入れないと指示文がほとんど効きません**。1 ステップに 2 回推論するので生成時間は倍近くになります |
| マスクの余白（`maskMargin`） | 48 | Runware の目安は 32〜64。マスクの周りごと切り出して拡大してから描くので、狭い範囲を塗ったときの精細さが上がります |
| モデルへ渡すマスクの広げ幅 | 16 px | **塗った縁に元画像が残るのを防ぎます**（下記） |
| 縁の余白 | 96 px | マスクが画像の縁に近いとき、その辺を単色で広げてから送ります（下記）。`maskMargin`（48）より広く取ります |
| 変化の強さ（`strength`） | 1 | **この値の既定は 0.8 で、低いほど元画像の影響が残ります**。修復モデルなので 1（＝完全に描き直す）にします。Runware のドキュメントは「FLUX Fill 系は `strength` を見ない」としていますが、このモデル自身のスキーマは既定 0.8 を宣言しているので、明示して曖昧さを消しています |
| negative prompt | `low quality, blurry, distorted, deformed, artifacts`（空欄時） | True CFG は対になる negative prompt があって初めて効くので、空欄のときだけ補います。**どんな絵でも避けたい破綻だけ**を並べていて、内容の方向づけはしません（公式作例は `nsfw` ですが、それは採っていません）。何か書けばそちらが優先されます |

- 値を推奨から外すと、実行ボタンの上に**なぜまずいかを表示**します。「**推奨値に戻す**」でいつでも戻せます
- スケジューラ・出力品質（JPG / WebP のときのみ）・プロンプトの強調記法（`sdEmbeds`）は「さらに細かい設定」から指定できます。スケジューラは「自動」のままで構いません（FLUX 系はフローマッチング前提です）
- 以前のバージョンで作った下書きは、空欄（モデル既定任せ）のまま保存されています。開いたときに一度だけ推奨値へ入れ替えます

#### 指示文の書き方

このモデルは用途ごとに書き方が決まっていて、そこを外すと結果が大きく変わります。プロンプト欄の下にボタンを置いてあります。

| 用途 | 指示文 |
|---|---|
| 描き替え（inpainting） | やりたいことをそのまま書く |
| **物体を消す** | 説明文ではなく **`remove` の 1 語**（説明文だと「消す」より「描く」方向に寄ります） |
| まわりを描き足す（指示なし） | `high-definition, perfect composition` |

#### 出していないパラメータ

`outpaint`（キャンバス拡張）・`hiresFix`・`layerDiffuse`・`pulid`・`ultralytics`・`controlNet`・`ipAdapters`・`acceleratorOptions`（TeaCache 等のキャッシュ高速化）・ウォーターマークは、この画面の用途から外れるか品質を落とすものなので出していません（送らなければ無効のままです）。

### Runware の LoRA（AIR）

Runware は LoRA を URL ではなく **AIR**（`provider:model@version` という独自の識別子）で指定します。Civitai のモデルは `civitai:<modelId>@<versionId>` でそのまま参照できますが、civitai.red のようなミラーや自前のモデルは参照できず、一度 Runware 側へ登録して AIR を発行してもらう必要があります。そのため fal / WaveSpeed とは別の欄になっています。

LoRA 欄の「**検索・取り込み**」で開くダイアログに、3 つの入り口があります。

**1. 登録済みから探す**（`modelSearch`）

- **「自分のモデル」を選ぶと、これまでに自分が Runware へアップロードしたものが一覧に出ます**。非公開・お気に入り・公開モデル全体にも切り替えられます
- 既定では、そのモデルで使えるアーキテクチャ（FLUX.1 Fill [dev] なら `flux1d`）だけに絞り込みます。チェックを外すと全部出ます
- 「使う」を押すと、控え（localStorage の `fal_runware_loras`）に入り、そのまま LoRA の行に追加されます。名前・トリガーワード・既定 weight は検索結果のものを引き継ぎます
- 検索に出てこない AIR は「AIR を直接指定する」から入れられます。`urn:air:flux1d:lora:civitai:1234@5678` のような長い表記で貼っても、`civitai:1234@5678` に直して受け取ります

**2. Civitai から**（アップロード不要）

- civitai.com のモデルページ URL を貼って「確認」すると、`civitai:<モデルID>@<バージョンID>` を組み立てて、それが Runware にあるかを `modelSearch` で確かめます
- あればそのまま使えます（Runware が Civitai を参照するので、こちらでアップロードする必要はありません）
- **無い場合はその旨を出します**。civitai.red などのミラーや Early Access のモデルはここでは参照できないので、下の 3 の経路を使ってください

**3. Hugging Face から**（`modelUpload`）

- Hugging Face に置いた `.safetensors` を Runware に取り込んで AIR を発行します。**取り込み元は Runware がダウンロードするので、公開アクセスできる URL である必要があります**
- 取り込み元は既存の **LoRA ライブラリからそのまま選べます**（名前・トリガーワード・既定 weight が初期値に入ります）。URL の直接入力も可
- civitai.red や自前のモデルは、まず生成画面と同じ「Civitai から取り込み」で Hugging Face へ上げてから、ここで登録します
- AIR は取り込み元の URL から決まる（`<名前空間>:<数値>@1`）ので、同じファイルを二度登録しても同じ AIR になります。手で書き換えることもできます
- **アーキテクチャの指定を間違えると、取り込めても生成では効きません**。ライブラリにベースモデルが記録されていればダイアログに出すので、それに合うものを選んでください
- 取り込みは検証 → ダウンロード → 最適化 → 保存 → 完了と進みます。REST には途中経過が流れてこないので `getResponse` で追い、段階を表示します。途中で閉じても Runware 側の処理は続くので、あとで 1 の一覧から拾えます

weight は -4〜4（負にすると、その LoRA の傾向から遠ざける方向に効きます）。0 は効果が無いのに枠を使うので送りません。

### マスク（塗った範囲だけを変える）

「マスクした部分だけを差し替える」をオンにすると、入力画像をなぞって編集する範囲を指定できます。扱いはプロバイダで変わります。

- **fal / WaveSpeed**: モデルには画像全体を渡し、返ってきた画像のうち**塗った範囲だけをブラウザ側で元画像に重ねます**。マスクは送信内容ではないので、塗り直せば編集し直さなくても結果が変わります。**重ねる前に、ずれを補正します**（下記）
- **Runware**: マスク画像（白 = 描き直す / 黒 = そのまま）を `maskImage` として**モデルに渡します**。マスクが送信内容の一部なので、描き直す範囲を変えるには編集し直しが必要です（重ね合わせだけは後からでも変わります）。このモデルはマスク前提なので、チェックは外せません

どちらの場合も、重ね合わせは**元画像の解像度**で行います（モデルへ送るのは学習解像度に合わせて縮めた画像なので、マスクの外側は元の画素がそのまま残ります）。

**合成画像は、送れる大きさに収まる形式で保存します。** 元解像度のまま PNG にすると、4000px 級の写真で 30〜45MB になります（実測: 4032×3024 で 41.4MB）。Worker の受け取り上限 40MB を超えるうえ、その大きさの POST は端末によっては通らず、Safari では `fetch` ごと落ちて **「マスクの合成に失敗しました…: Load failed」** になっていました。可逆の PNG を第一候補にしつつ、12MB に収まらなければ WebP → JPEG と落とします（同じ画像が 8.3MB に収まります）。スクリーンショットやイラストのように PNG がよく効く絵は、そのまま PNG のままです。WebP を書き出せない端末（Safari 17 より前）では JPEG になります。

大きな本文の POST は一度で通らないことがあるので、**一度だけ間を置いて送り直します**。それでも駄目なときは、送信サイズと理由を添えた文言にします（英語の "Load failed" だけにしない）。

**マスクが画像の縁に近いときは、その辺を単色で広げてから送り、返ってきた画像を元の枠で切り出します。** `maskMargin` は「マスクの周りごと切り出して拡大し、修復してから元に戻す」処理で、**最小 32・無効にできません**。マスクが縁に近いとこの切り出しが画像内に詰められ、その辺だけ処理が変わって元画像が縁に残ります。あらかじめ広げておけば、モデルから見てマスクは常に画像の内側にあるので、どの辺も同じ扱いになります。

- 広げるのは**必要な辺だけ**です（マスクの外接矩形が「縁の余白」px より近い辺）。中央だけ塗ったときは何も足しません
- 余白の色は**元画像の外周の平均色**の単色です。マスクは縁を外へ伸ばして余白の中まで続けるので、縁まで塗った場合はモデルから見た「マスクの境目」が元画像の外に出ます
- 送信サイズは 64 の倍数・2048px までなので、はみ出す場合は全体を縮めます。**元画像の縦横比は変えません**
- 何をどう送るかは、送信サイズの説明に出ます（例:「マスクが縁に近いので 上 に余白を足し、1024×1152 で送って元の枠で切り出します」）

**モデルには、塗った範囲より少し広いマスクを渡します。** 修復モデルは輪郭のすぐ内側に元画像を引きずりがちです（潜在空間では 8px 角がひと単位なので、境目はどうしても混ざります）。そこでモデルへ渡すマスクだけを既定 16px ぶん広げ、はみ出したぶんは合成で捨てます。**出来上がりの範囲は塗ったままで変わりません。** 縁に元画像が残るときは「広げる px」を上げてください。

**塗った範囲は必ず 100% 差し替わります。** 縁のぼかしは輪郭の外側にだけ広がり、塗った内側は振り切ります（ぼかしただけだと輪郭を中心に内外へ均等ににじむので、細い塗りに強いぼかしをかけるとマスクがどこも 100% に届かず、塗った範囲の全体に元画像が混ざったままになります）。

**その 100% の境目には、白い実線を引きます。** 外側を暗くするだけでは、ぼかしを強くしたときに「どこからが完全に差し替わるのか」が濃淡から読み取れませんでした。線は塗った形そのもの（＝ぼかす前の輪郭）に沿って引きます。ぼかしがあるときは、そのさらに外側に**にじみが届く先を示す細い線**も出します。塗った側に乗せる色は薄くしてあるので、元の絵を見ながら範囲を決められます。

**ブラシは置く前に太さが分かります。** カーソルに合わせて円を出し、消しゴムのときは破線にして塗りと取り違えないようにしています。

**画像の端まで塗った場合**、その範囲は端まで有効なままです。縁のぼかしをかけるとき、画像の外側は「縁の画素が続いている」ものとして扱っているためです（そうしないと外側の透明と混ざって端で濃度が半分ほどに落ち、画像のふちに沿って元画像が帯状に残ります）。

**入力画像を差し替えると、塗った範囲は消えます**（前の画像の形に合わせた範囲を、関係のない画像へそのまま当ててしまわないため）。消したことは画面にも表示します。ブラシの太さと縁のぼかしの設定はそのまま残ります。下書きの復元と、履歴の「マスクを調整」で開き直したときだけは、同じ画像に戻すので範囲も引き継ぎます。

入力画像は data URI として渡します。このアプリは Cloudflare Access の内側に置く前提で、`/api/image/...` をプロバイダ側から取得できるとは限らないためです。なお **WaveSpeed に指定する LoRA は公開アクセスできる URL である必要があります**（非公開の Hugging Face リポジトリに置いた LoRA は使えません）。

Runware は投入も結果取得も `https://api.runware.ai/v1` への POST（タスクの配列）で行います。生成のあいだ接続を掴んだままにしないよう `deliveryMethod: "async"` で投入し、`getResponse` タスクで結果を取りに行きます。画像は `seedImage` / `maskImage` としてタスクのトップレベルに置きます（Playground のスキーマには `inputs` でまとめる形も載っていますが、このモデルの API は受け付けません）。

## LoRA ライブラリの管理

LoRA には**ベースモデル**（Krea 2 / Qwen など）を持たせていて、各画面はそれに合うものだけを候補に出します（生成画面と比較アリーナは Krea 2、画像編集は Qwen）。別のベースモデル向けを隠したときは件数を知らせます。

- Civitai から取り込むと、ベースモデルとトリガーワードは Civitai の情報から自動で入ります
- Hugging Face の一括登録では、ダイアログでベースモデルを選べます（既定は今のモデル）
- ベースモデルが未設定だった既存の LoRA は、初回だけ「Krea 2」として扱うよう自動で移行します。違うものはライブラリ管理で直せます

LoRA 欄の「ライブラリを管理」（`library.html`）で、登録済み LoRA の情報をまとめて編集できます。

- **表示名**: プルダウンと一覧に出る名前を自由に付けられます。**生成時に送られるファイル名は変わりません**（Modal 系は LoRA を URL ではなくファイル名で指定するため、表示名と送信名は分けてあります）
- **トリガーワード**: 生成画面の LoRA 行にチップで表示され、「挿入」でプロンプト末尾に足せます（すでに書かれている語は足しません）
- **既定 scale**: その LoRA を行に追加したときの初期値になります
- **ベースモデル・メモ・お気に入り**: 一覧の絞り込みと並び替えに使います。★ はプルダウンでも先頭に来ます
- **Civitai の情報を取得**: 取り込み時にモデルの隣へ保存した `<ファイル名>.civitai.json` を読み、トリガーワード・ベースモデル・モデル名・取り込み元を補完します（Worker の `/api/lora/meta` 経由。非公開リポジトリにも対応）。**手で編集済みの項目は既定で上書きしません**（反映する項目を選べます）
- 「要整理」フィルタは、まだ情報を取得しておらずトリガーワードも入っていないものを集めます。「未取得をまとめて取得」で一括補完できます

保存先は生成画面と同じ `fal_lora_library`（localStorage）で、追加した項目はすべて任意です。古いデータや、この画面を使わない場合の動作は変わりません。端末間同期も既存の `loras` セクションをそのまま使います。

## テスト

テストは追加の依存なしで動きます（Node だけ）。

```
node test/import.test.mjs        # Civitai 取り込みパイプライン
node test/modal.test.mjs         # Modal（modal_comfy）ジョブ・ポーリングの扱い
node test/history.test.mjs       # 履歴 API（一覧の軽量化と 1 件取得）
node test/lora-library.test.mjs  # LoRA ライブラリ（Modal へ渡す識別子など）
node test/store.test.mjs         # localStorage のラッパー（容量あふれの扱い）
node test/gallery-pager.test.mjs # ギャラリーの分割描画
node test/history-feed.test.mjs # 履歴のページ送り取得
```

前の 3 つは `worker.js` をそのまま Node に読み込み、Civitai / Hugging Face / R2 / Modal / D1 をモックして流します。**D1 のモックは `node:sqlite` で本物の SQLite を動かします**（並び替え・ページ送り・参照の数え上げが SQL に乗っているので、作り物にすると肝心なところが検証できません）。取り込みのテストはサイズ関連の定数を小さくパッチするので、1 MB のダミーファイルでも「複数回の alarm 実行に分割される」実際の経路を確認できます。`DEBUG_ERRORS=1` を付けると、再試行のために握りつぶしている例外を表示します。後ろの 4 つはブラウザ用の `lora-library.js` / `store.js` / `gallery-pager.js` / `history-feed.js` を `node:vm` や最小の DOM スタブで読み込み、`localStorage` や `IntersectionObserver`・`fetch` だけ差し替えて確かめます。

## LoRA 比較アリーナ

サイドバーの「比較アリーナ」から開く別画面で、20〜30 個規模の LoRA チェックポイントをまとめて比較・順位付けできます。

- **セッション**: 比較したいチェックポイント群を選んで作成する単位。ライブラリの一覧から個別に選べるほか、**2 つの LoRA を範囲指定するとその間（名前順 = バージョン番号順）のチェックポイントが全部まとめて選択**されます
- **ラウンド**: セッション内でプロンプトを入力して「生成する」と、全チェックポイントで同じ seed・同じ設定の画像を一斉生成します。プロンプトを変えて何度でも実行できます
- **匿名比較**: 生成後、2 枚の画像がどのチェックポイントか伏せた状態で表示されるので、良い方に投票します（← / → キー、引き分け・スキップ可）。左右の並びはランダムで、対戦の組み合わせは「未対戦 → 対戦数が少ない → レートが近い」順に自動で選ばれます
- **Elo レーティング**: 投票結果から Elo レート（初期値 1000・K=32）を計算してリーダーボードに表示します。集計範囲は「セッション全体」と「各ラウンドのみ」を切り替えられます
- 生成画像は type: compare の履歴として保存されるため、**通常の生成画面のギャラリーにもそのまま表示**されます（ギャラリー側で履歴を削除するとアリーナ側の画像表示も消えるので注意）
- セッション・投票結果は LoRA ライブラリと同じ仕組みでサーバーに自動同期され、全端末で共通です
- 生成中にタブを閉じても、次にアリーナを開いたときに未完了のラウンドのポーリングを再開します

## 部分AI編集

サイドバーの「部分AI編集」から開く別画面で、画像の一部だけを AI で編集して元画像にはめ込みます。

1. 画像を読み込み、ドラッグで編集したい範囲を選択（比率プリセット・縦横切替・移動・リサイズ対応）
2. 編集プロンプトとモデルを指定して実行すると、切り抜きが Poe の画像編集ボットに送られます（「追加プロンプト」欄に入力があれば、編集プロンプトの末尾に改行でつないで送ります）
3. 返ってきた編集結果をブラウザ内で元画像にはめ込み合成します（Lanczos3 縮小・外周のカラーマッチ・境界のフェザーブレンド）

### 使い方のメモ

- 生成は [Poe の OpenAI 互換 API](https://creator.poe.com/docs/external-applications/openai-compatible-api) 経由で、**課金は Poe のポイント**です（fal ではありません）。Worker の Secret に `POE_API_KEY` の設定が必要です
- モデルは Nano Banana 2 / Nano Banana Pro / GPT Image 2（品質指定つき）のほか、カスタム欄に任意の Poe ボットハンドルを指定できます（カスタム時はボット固有パラメータを送りません）
- アスペクト比は選択範囲から最も近いプリセットが自動選択され、長辺 512px 未満の切り抜きは送信前に拡大されます
- Poe の呼び出しはサーバー側（Worker のジョブ）で完結します。生成中にタブを閉じても、次に編集画面を開いたときに続きから再開されます
- 結果は生成履歴に保存され、トップのギャラリーに表示されます（画像は 合成結果 / AI 編集後 / 切り抜き / 元画像 の 4 枚。履歴の削除で一括削除）
- 編集プロンプトはひな形として置いておき、そのつど書き足したい指示は「追加プロンプト」欄に入れます。入力があるときだけ、`{NAME}` を置換したあとの編集プロンプトの末尾に改行でつないで送信します（追加プロンプト側の `{NAME}` も同じ名前で置換されます）。空欄なら何も足しません。どちらの欄も端末ごとに下書きとして保存されます
- 「はめ込み合成の設定」で境界ブレンド幅とカラーマッチ幅（いずれも選択範囲の短辺に対する %）を調整できます

## データの保管先

| データ | 保管先 | 備考 |
|---|---|---|
| fal API キー / Modal トークン | Worker の Secret | ブラウザには一切渡らない |
| 生成履歴（プロンプト・設定・結果） | サーバー（**D1** の `history` 表） | **件数の上限なし**（消えるのは明示的に削除したときだけ）。全端末で共通。一覧（`GET /api/history`）はマスクを外した 1 ページぶんを返し、続きの位置を `X-Next-Cursor` で示す。マスクが要るときだけ `GET /api/history/<id>` で 1 件取る |
| 履歴に載っている画像への参照 | サーバー（D1 の `history_images` 表） | 画像 1 枚が複数の記録に出る（編集の入力に使い回したときなど）ので、参照の数え上げに使う。`/api/capture` の「その URL は履歴に載っているか」もここを引く |
| 生成画像 | サーバー（R2 バケット `fal-playground-images`） | fal / WaveSpeed / Runware の CDN からも取り込むため**失効しない**。履歴の削除と連動して削除するが、**ほかの記録がまだ載せている画像は残す**（`history_images` の参照を数える）。R2 移行前の画像は旧 Durable Object から後方互換で配信 |
| LoRA ライブラリ | サーバー（自動同期） + localStorage | 全端末で共通。どの画面から登録しても同期されます（生成 / 画像編集 / ライブラリ / 比較アリーナ） |
| Runware の LoRA（AIR）の控え | localStorage | 端末ごと。実体は Runware 側にあるので、「Runware から取り込み」で再取得できる |
| 比較アリーナのセッション・投票結果 | サーバー（自動同期） + localStorage | 全端末で共通。画像は生成履歴と共用 |
| フォームの下書き・テーマ | localStorage | 端末ごと（意図的に同期しない） |
| 生成履歴の表示キャッシュ | localStorage | 端末ごと。開いた直後にギャラリーを描くためだけのもので、直近 60 件・マスクのストロークを除いた形で持つ（正はサーバー） |
| 部分AI編集の作業状態（元画像・選択範囲・プロンプト） | localStorage + IndexedDB（元画像） | 端末ごと。再読み込みしても復元される |

### localStorage の容量あふれ

localStorage はブラウザごとに 5MB 前後で頭打ちになり、超えると `QuotaExceededError`（Safari の文言は "The quota has been exceeded."）を投げます。**この例外はアプリの外へ出しません**（`store.js` の `falStore`）。

- 素の `setItem` を呼んでいた頃は、いっぱいになった端末で**生成の途中**（送信済みジョブの控えを書くところ）に例外が飛び、走っているジョブがエラー扱いになって落ちていました。fal 側では成功しているのに結果を取り逃がし、画面には英語のまま "The quota has been exceeded." だけが出ます
- 書けなかったときは、捨ててよいキャッシュ（生成履歴の表示キャッシュ）を落として一度だけ書き直します。それでも駄目なら諦めます。下書き・ジョブの控え・キャッシュは、失っても次に開けば取り直せるものばかりです
- ライブラリへの登録のように**失うと困るもの**だけは、`setOrThrow` で日本語の理由（「この端末の保存領域がいっぱいで…」）を出します
- あふれさせない側の手当てとして、生成履歴の表示キャッシュは直近 60 件・マスクのストロークを除いた形で持ち、マスクの座標は 4 桁に丸めて保存します（長辺 2048px でも 0.2px の差なので形は変わらず、ストローク 1 本あたりの JSON が半分以下になります）

### 生成設定の画像への焼き込み

保存される PNG には、生成設定（プロンプト・モデル・LoRA・seed・サイズなど）の JSON が **iTXt チャンク（キーワード `playground`）** として埋め込まれます。ComfyUI がワークフローを画像に埋め込むのと同じ発想で、「保存」でダウンロードした画像ファイルだけから後で設定を確認できます（画質への影響はありません）。fal のモデルが JPEG を返した場合は焼き込みされませんが、履歴レコード側に設定が残ります。

## Modal 自前ホスト版 Krea 2

モデル選択の「Krea 2 [turbo] 自前ホスト（Modal 実験版 / GPUスナップ版 / 本番 / チェックポイント指定版 / 統合版 / LanPaint 版）」は、fal ではなく Modal 上の [modal_comfy](https://github.com/rabi0424/modal_comfy) API で生成します。実験版（CPU スナップショット）・GPU スナップショット版（`krea2-comfy-api-gpusnap`）・本番（安定版）・チェックポイント指定版（`krea2-comfy-api-ckpt`）・統合版（`wan-vace-api`）・LanPaint 版（`lanpaint-api`）はモデル選択で切り替えられ、標準は実験版です。エンドポイントの URL 自体を変えたい場合は、Worker の環境変数で上書きできます（未設定なら modal_comfy の既定 URL）:

- `KREA2_ENDPOINT_EXP` = 実験版の URL
- `KREA2_ENDPOINT_GPUSNAP` = GPU スナップショット版の URL
- `KREA2_ENDPOINT` = 本番の URL
- `KREA2_ENDPOINT_CKPT` = チェックポイント指定版の URL
- `WAN_ENDPOINT_GENERATE` = 統合版（生成）の URL
- `WAN_ENDPOINT_EDIT` = 統合版（Wan2.2 + VACE のマスク編集）の URL
- `LANPAINT_ENDPOINT_GENERATE` = LanPaint 版（生成）の URL
- `LANPAINT_ENDPOINT_INPAINT` = LanPaint 版（インペイント）の URL

### 統合版（編集とコンテナを共有）

統合版は、画像編集の「Modal 自前ホスト（Wan2.2 + VACE）」と**同じコンテナを共有**します。どちらかのリクエストでコンテナが立ち上がればもう一方もウォームになるので、生成と編集を行き来する使い方ではコールドスタートとアイドル維持のコストが 2 用途で割り勘になります（同時実行は 1 件なので、両方に同時に投げると後発は待たされます）。

チェックポイント指定に加えて、詳細設定でサンプラー・スケジューラ・denoise も指定できます（空欄なら API の既定 `er_sde` / `simple` / `1.0`）。

### LanPaint 版（インペイントとコンテナを共有）

LanPaint 版は、画像編集の「Modal 自前ホスト（LanPaint インペイント）」と**同じコンテナを共有**します。統合版とはコンテナが別なので（モデルが別物で統合できないため）、**編集で LanPaint を使うなら生成もこちらに寄せるとコンテナが 1 つで収まります**。API は統合版と同じで、チェックポイント指定とサンプラー・スケジューラ・denoise も使えます。

### チェックポイント指定版

チェックポイント指定版を選ぶと「チェックポイント」欄が出て、生成に使う UNet を LoRA と同じ感覚で切り替えられます。既定は `Krea-2-Turbo-Q8_0.gguf` です。

- **Hugging Face から一括登録**: 公開リポジトリの `.safetensors` / `.gguf` を一覧から選んでチェックポイントライブラリに登録できます（既定リポジトリは `Abiray/Krea-2-Turbo-GGUF`）。登録した URL のチェックポイントは**初回使用時に Modal 側が Volume へ自動取り込み**します（サイズにより 1〜数分。2 回目以降はキャッシュ）。`HF_TOKEN` が設定されていれば非公開リポジトリも使えます
- **Civitai から取り込み**: LoRA と同じサーバー側パイプライン（Civitai → HF アップロード）で取り込み、チェックポイントライブラリに登録します。R2 の一時保存は multipart 対応なので大きなチェックポイントも扱えます（安全弁として約 30 GB まで）。一時ファイルは取り込み完了・失敗時に削除されます
- **転送の並列化と再開**: Range 対応かつ SHA256 公称値のあるファイル（64 MB 超）は 4 並列の分割ダウンロードで取り込み、HF へのアップロードも並列化しています。パート単位で進捗が保存されるため、回線が不安定でも完了した分はやり直しになりません。さらに、1 回の実行で転送するのは最大 16 パート（または 2 GB）までで、そこで一旦中断して次の実行に続きを渡します。Workers / Durable Object の 1 呼び出しあたりの上限（CPU 時間・subrequest 数）に当たって実行ごと打ち切られるのを防ぐためで、これにより数十 GB のチェックポイントでもファイルサイズに関係なく一定の負荷で取り込めます（HF へのアップロードは、複数回に分かれても同じ multipart セッションを使い続けられるよう転送先の一覧を R2 に保存します）。転送 1 本ごとにタイムアウトを設けており、応答が返らなくなった接続は切って残りのパートから再開します。Civitai の API 問い合わせや HF の制御系リクエストにも 60 秒のタイムアウトを設けているので、相手が応答を返さないまま接続だけ生きている場合でも「モデル情報を確認中…」のまま止まりません（失敗理由を表示して終了します）。進捗が 15 分まったく動かないジョブは中断してエラーを表示します（ダウンロード中の表示のまま止まり続けたり、取り込みボタンが塞がったままになったりしないため）。この経路ではダウンロード全体の SHA256 逐次検証の代わりに、各パートの長さ検証 + Civitai 公称ハッシュを LFS の oid として使います
- プルダウンの「URL / ファイル名を入力…」で、HF の resolve URL（自動登録されます）や Volume 内のファイル名の直接指定もできます
- Volume に無いファイル名を指定するとエラーになり、利用可能なファイルの一覧がエラーメッセージに表示されます
- `.gguf` は GGUF ローダー、`.safetensors` は ComfyUI 標準の UNET ローダーで読み込まれます（Krea 2 系アーキテクチャのもの以外は動きません）
- ライブラリは LoRA ライブラリと同様に全端末で同期されます

### 使い方のメモ

- LoRA はライブラリの項目なら **Hugging Face の resolve URL のまま**送られ、Volume に無ければ Modal 側が初回リクエスト時に取り込みます。「Hugging Face から一括登録」で `tottie2215/temp_str`（既定で入力済み・開くと自動読み込み）から Krea-2 用 LoRA（`Shimizu_krea2_v1_000005000` など）を登録しておけば選ぶだけで使えますが、**他のリポジトリから登録したものも同じように使えます**。一覧は追加日の新しい順で、ファイル名で絞り込めます。URL 欄に Volume 内のファイル名を直接入力しても OK（その場合に探されるのは Volume と `tottie2215/temp_str` の直下だけです）
- ステップ数のデフォルトは 8（変更非推奨）、ガイダンス（cfg）は 0〜1 の範囲
- アイドル状態からの初回生成（コールドスタート）は 1 分ほどかかります。ウォーム時は 10〜20 秒程度
- 複数枚指定時は 1 枚ずつ順番に生成されます（2 枚目以降はウォームなので速い）
- 生成はサーバー側（Worker のジョブ）で完結します。生成中にタブを閉じたり通信が切れたりしても結果は失われず、ページを開き直せば途中から再開されます
- 「キャンセル」は結果の受け取りをやめるだけで、Modal 側で開始済みの生成処理は止まりません
- 比較モードは fal のキュー API 専用のため、Modal 版では使えません

## 表示の軽さ（履歴まわり）

履歴は上限なく貯まり、生成・部分AI編集・画像編集の 3 画面がページを開くたびに取りに来ます。ここが重いと、スマホではメニューを移るたびに固まって見えます。手当ては 3 つです。

- **一覧はマスクを外して返す**（`GET /api/history`）。画像編集のマスクは塗った線の座標をそのまま持つので、1 レコードで数十 KB になります。一覧に必要なのはサムネとプロンプトだけなので落とし、`masked` の印だけ残します。マスクが要るのは「マスクを調整」で開き直すときだけなので、そのとき `GET /api/history/<id>` で 1 件を丸ごと取り直します（保存時の `POST` の応答は今までどおりマスク込み）
- **一覧はページで返す**（`?limit=` / `?cursor=`・既定 500 件）。続きがあるときは `X-Next-Cursor` ヘッダで位置を示します（中身は前のページ最後の `seq`）。3 画面とも「全件を手元に持って絞り込む」作り（ギャラリー検索も統計もそこに乗っています）なので、`history-feed.js` が続きを裏で追い、**取れたページから順に描きます**。最初の 1 ページが届けば画面が出るので、件数が増えても表示までの待ち時間は変わりません
  - 本文を配列のままにしてページ位置をヘッダに置いたのは、デプロイ直後にまだ古い JS を持っているタブでも、直近の 1 ページぶんはそのまま表示できるようにするためです
- **ギャラリーは見えたぶんだけ並べる**（`gallery-pager.js`）。最初は 30 件、末尾が近づくたびに 30 件ずつ足します。並べた件数は描き直しをまたいで保つので、下までスクロールしてからサムネを選んでも先頭には戻りません。`IntersectionObserver` が無い環境では全件並べます（従来どおり）

なお、いま裏で追うのは**全件**です。カタログは D1 に移したので `WHERE prompt LIKE ...` や FTS5 をサーバー側で引けるようになりましたが、**検索と統計はまだクライアント側**にあります。数万件の規模まで貯めるなら、ここをサーバーへ寄せるのが次の一手です（そうすれば全件を手元に持つ必要そのものが無くなります）。

履歴サムネイルは**縮小版を作らず原寸のまま**です。サムネのつもりで保存した画像が縮小版だった、という取り違えを避けるためで、表示の軽さより優先しています。

### 履歴の保管レイアウト（D1）

履歴のカタログは **D1（SQLite）の `history` 表**に置きます。定義は `schema.sql`。

| 列 | 用途 |
|---|---|
| `seq` | 並び順（主キー）。大きいほど新しい。同じ id を保存し直すと振り直されて先頭に来る |
| `id` | 履歴レコードの id。1 件取得・削除のルートが受ける形（`[\w.-]{1,100}`）だけ通す |
| `source` | 何が作ったか。この画面の生成物は `playground` |
| `type` / `created` / `model` / `prompt` | 絞り込み・並び替え・（将来の）検索に使う列 |
| `record` | レコード全体の JSON。**ただしマスクは含まない** |
| `mask` | 画像編集のマスク（塗った線の座標）。1 件で数十 KB になるので列を分ける |

**なぜ Durable Object の KV をやめたか。** もとは 1 レコード 1 キー（`hist:<id>`）+ 1 件 1 キーの索引（`hidx:<逆順の通し番号>:<id>`）で持っていました。件数の上限を外すために、並び順を辞書順で引けるキーに埋め込み、通し番号を自前で振り、差し替えで残った古い索引を突き合わせて弾く、という仕組みを手で書いていたわけです。**これは SQLite の上に KV を敷いて、その上に索引を作り直していたのと同じ**でした（Durable Object の保管先はもともと SQLite です）。D1 に移すと、その全部が `INTEGER PRIMARY KEY` と `ORDER BY seq DESC LIMIT ?` になります。

もう 1 つの理由は**共有**です。アーカイブ側のアプリからも同じカタログを読み書きしたいのですが、Durable Object は 1 インスタンスが単一スレッドなので、そこを通すと直列点をもう 1 つ作ることになります。D1 なら両方の Worker が直接バインドできます。`source` 列があるので、「playground のギャラリー」と「アーカイブの横断検索」は同じ表への別クエリになります。

- ページ送りは `WHERE source = ? AND seq < ? ORDER BY seq DESC LIMIT ?`。カーソルは前のページ最後の `seq`（ただの整数）です
- 一覧の `SELECT` は `mask` 列を選ばないので、マスクは転送量にもパース時間にも乗りません
- 保存は「同じ id を消す → 入れ直す」の 1 バッチ。書く量は件数に依りません

**画像の参照は `history_images` 表**（`url` × `history_id`）に持ちます。1 枚の画像が複数の記録に出ることがある（編集の入力に使い回したときなど）ので、削除のたびに残りの参照を数え、**参照が無くなったものだけ R2 から消します**。以前は記録を消すと、その記録が載せている画像を無条件に消していたので、同じ画像を使っている別の記録から画像が消えることがありました。`/api/capture` の「その URL は履歴に載っているか」も、全件走査ではなくこの表の 1 行引きになります。

#### Durable Object からの移行

以前のレイアウトが残っていれば、履歴に最初に触れたときに自動で D1 へ移します。`history:list`（全件を 1 キー）・`history:order`（id の配列）・`hidx:` 索引のどこからでも移行でき、**並び順（`seq`）はそのまま引き継ぎます**。

- **新しい方から移します。** 移行の途中でもギャラリーの先頭（＝よく見るところ）は D1 側に揃っているので、見た目には気づきません
- 無料プランの D1 は **1 リクエストあたり 50 クエリ**までなので、1 回で移すのは予算のぶんだけです。終わらなければ次のアクセスで続きます
- 引き取ったぶんは Durable Object から消すので、二重には持ちません。空になったら `meta` に印を付け、以後この経路は通りません
- 移行が済むと、この Durable Object に残る仕事は**生成・取り込みのジョブ実行だけ**になります（alarm が要るもの＝本来 Durable Object が向いている用途）

#### 無料プランで効いてくる上限

| 項目 | 無料 | 有料 |
|---|---|---|
| D1 の 1 データベース | 500MB | 10GB |
| D1 の 1 リクエストあたりのクエリ数 | 50 | 1000 |
| 1 クエリの bound parameter | 100 | 100 |

複数行 INSERT は 100 個の bound parameter に収まるよう刻んでいます（`insertStatements`）。全消しも 1 リクエストでは終わらないことがあるので、`DELETE /api/history` は `{ ok, done }` を返し、`done: false` のあいだクライアントが送り直します。

### 画面遷移とキャッシュ

`_headers` で HTML・CSS・JS に `stale-while-revalidate` を付けています。既定の `max-age=0, must-revalidate` のままだと、画面を移るたびに 1 つずつ再検証の往復が入り、中身が変わっていなくてもそのぶん遅れます。

- CSS / JS は 7 日、**HTML は 1 日**の窓です。HTML は遷移の起点で、これが返るまで CSS も JS も要求できないため、この 1 往復がメニューを移るたびの待ち時間にそのまま乗っていました
- HTML の窓を短くしてあるのは、続けて行き来している間（＝往復が効く場面）だけ速さを取り、しばらくぶりに開いたときは新しい版から始めるためです
- `max-age` は 0 のままなので更新は必ず次の 1 回で反映されます。代償は**デプロイ直後の 1 回だけ古い HTML が出る**ことです
- `_headers` のパターンは互いに重ならないようにしてください。複数のルールに当たると値がカンマで連結されます

## 開発メモ

- ローカルの静的サーバー（`python3 -m http.server`）でも UI の確認はできますが、生成・履歴・同期はすべて Worker の API（`/api/*`）に依存するため動きません。実際の動作確認は Cloudflare へのデプロイで行ってください
- Access のセッションが切れると API がログインページへのリダイレクトになります。アプリはこれを検出して「再読み込みしてサインインし直してください」と表示します
